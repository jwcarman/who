# who 0.10.0: security fixes (design)

Date: 2026-11-07
Status: scope agreed in conversation (fix the security review's findings, release, then build passwordless
on top); written spec pending review
Branch: `security-fixes` (from `main`)
Evidence: an independent security review of `main` (2026-11-07), recorded in this conversation; finding ids
below are the review's.

## Why

who becomes the identity layer of the noir platform and of every customer app built on it. A review of
`main` (0.9.0 on Maven Central) found two critical flaws in enrollment, a filter that authenticates outside
Spring Security, and several fail-open or leaky paths. Nobody uses who yet, so the fixes may change behaviour
where the safer design requires it; the release is **0.10.0**.

The passwordless work (`passwordless` branch) is rebased onto this release afterwards.

## Fixes

### C1. Secrets come from `SecureRandom`, never from UUIDs

Enrollment token values are generated by the same monotonic UUIDv7 generator as their ids, so a value is its
id plus one.

- New `org.jwcarman.who.core.crypto.Secrets` in who-core: `static String token()` returns 32 bytes (256 bits)
  from one shared `SecureRandom`, encoded URL-safe Base64 without padding (43 characters). Not
  `getInstanceStrong()` (it can block). The class must initialize at run time in a native image (GraalVM's
  default); nothing may create the `SecureRandom` at build time.
- Enrollment token values use `Secrets.token()`. API keys use it too (`"who_" + Secrets.token()`), replacing
  their own `SecureRandom` code.
- Identifiers stay UUIDv7 (`Identifiers.uuid()`); its Javadoc says ids are not secrets.
- Values are still stored only as SHA-256 hashes.

### C2. Enrollment redemption is atomic

Today `enroll` reads, checks `PENDING`, links, then saves `REDEEMED`; two concurrent calls both succeed.

- `EnrollmentTokenRepository` gains `boolean redeem(UUID id, Instant now)`:
  `UPDATE who_enrollment_token SET status = 'REDEEMED', redeemed_at = :now WHERE id = :id AND status = 'PENDING'
  AND expires_at > :now`, true when one row changed.
- `enroll(tokenValue, credential)`, in one transaction: find the token by hash; if `redeem` returns false,
  link nothing and throw (expired → `EnrollmentTokenExpiredException`, otherwise
  `EnrollmentTokenNotPendingException`, chosen by rereading the row); only then link the credential.

### I1. The API-key filter runs only inside a security chain

`ApiKeyAuthenticationFilter` is a `Filter` bean, so Spring Boot also registers it with the servlet container
for every path, after the security chain.

- Autoconfiguration registers a `FilterRegistrationBean` for it with `setEnabled(false)`.
- New `WhoApiKeySecurity.apiKey()` (a `Customizer<HttpSecurity>`) adds the filter before
  `AuthorizationFilter`; apps apply it to the chains that accept API keys:
  `http.with(WhoApiKeySecurity.apiKey(), Customizer.withDefaults())`.
- The filter authenticates only when no authentication is already present; a key sent by an already
  authenticated caller is ignored (it never replaces the principal).

### I3. JWT: 401, never 500, and documented issuer validation

- `WhoJwtAuthenticationConverter` reads `iss` with `getClaimAsString("iss")` and `sub` likewise; a missing
  claim throws `BadCredentialsException` (401). A non-URL issuer (e.g. `"noir"`) works.
- The README recommends `issuer-uri`, or an explicit `JwtIssuerValidator` with `jwk-set-uri`.

### I4. Enrollment binds only an authenticated redeemer's credential, to an active identity

- `enroll` refuses an identity that is not `ACTIVE`: new `EnrollmentIdentityInactiveException`, nothing
  redeemed or linked.
- Javadoc and README: the credential must come from the redeemer's own authentication (for JWT, the
  validated token's issuer and subject), never from the request body. The README snippet is fixed: it
  persists the `JwtCredential` before enrolling, from the authenticated `Jwt`.
- A credential already linked to an identity: `enroll` throws `CredentialAlreadyLinkedException` instead of
  letting `DuplicateKeyException` become a 500.

### I5. Method security is on by default

- The starter enables method security (`@EnableMethodSecurity`) when the application has not configured it,
  controlled by `who.method-security.enabled` (default `true`). An app that wants its own configuration sets
  it `false`.
- README: `@RequiresPermission` needs method security, and the starter turns it on.

### I6. No secrets in messages, logs or the example

- `EnrollmentTokenNotFoundException` no longer includes the submitted value ("Enrollment token not found").
- `EnrollmentToken.toString()` masks `value` (`value=***`).
- The example keeps showing the access token (its quick start depends on it), under a heading that says it is
  shown for the demo only, and the README says real apps never render tokens.

### Minor fixes

- `EnrollmentToken.revoke()` keeps `redeemedAt`; `revokeToken` is `@Transactional`.
- `who_identity_role.identity_id` gets a foreign key to `who_identity(id)` with `ON DELETE CASCADE`.
- Deleting an API key (`ApiKeyService.revoke(UUID id)`, new) removes its credential row and its identity link.
- `PermissionsResolver`'s Javadoc matches behaviour (one resolver).

## Testing

- **On PostgreSQL.** Repository and service tests run against PostgreSQL 17 (Testcontainers), the production
  engine, instead of H2. A shared test fixture provides the container.
- **C1:** a token value is 43 URL-safe Base64 characters, not a UUID, and unrelated to its id (many tokens:
  no value equals or is adjacent to any id); `Secrets.token()` values are distinct across 10,000 calls.
- **C2:** two threads redeem one token at once: exactly one succeeds, the other gets
  `EnrollmentTokenNotPendingException`, and exactly one credential is linked. An expired token links nothing.
- **I1:** in a web application context the filter is not registered with the servlet container; through a
  chain with `apiKey()` a valid key authenticates; on a chain without it, a key does nothing; a key sent by an
  authenticated caller does not replace the principal.
- **I3:** missing `iss`, missing `sub` and a non-URL `iss` give 401 (MockMvc with a resource-server chain).
- **I4:** a suspended identity's token is refused and nothing is linked; linking an already linked credential
  throws `CredentialAlreadyLinkedException`.
- **I5:** with the starter, `@RequiresPermission` is enforced with no `@EnableMethodSecurity` in the app; with
  `who.method-security.enabled=false` the starter does not enable it.
- **I6:** the not-found message contains no token; `toString()` contains no value.
- **Minors:** revoking keeps `redeemedAt`; deleting an identity removes its role assignments; revoking an API
  key removes its row and link.
- All existing tests still pass.

## Out of scope

Everything passwordless (its own spec, rebased later), Spring Boot 4.1 (with passwordless), native-image work,
the review's design findings D1–D7 (they belong to the passwordless spec), validating permission strings at
startup, and releasing (the owner publishes the GitHub release, which sets the version).
