# who 0.12.0 (design)

Date: 2026-11-07
Status: design for review
Inputs: the noir-app-template build (its final review and ledger list who friction found by a real
app), the conversation about sessions and Spring Session JDBC, and the 0.11.0 backlog.

## Why

who 0.11.0 shipped passwordless sign-in and native support. Building the first real app on it
(noir-app-template) found where who's API makes an app work around it, and where sessions need to be
ready for more than one instance. 0.12.0 closes those gaps. It is additive except where noted.

## 1. Sessions ready for Spring Session

Apps will store sessions with Spring Session JDBC, so they survive restarts and work across
instances. who keeps only `WhoSession(identityId, credentialId, signedInAt)` in the session.

- **No saved requests.** `WhoWebSecurity.passwordless()` sets `requestCache(c -> c.requestCache(new NullRequestCache()))`.
  An SPA receives a plain 401 and handles navigation itself, so the default `HttpSessionRequestCache`
  only puts a copy of the request (headers and cookies included) into the session.
- **Principal index.** When `WhoSessionSecurityContextRepository` saves a `WhoSession`, it also sets
  the attribute `org.springframework.session.FindByIndexNameSessionRepository.PRINCIPAL_NAME_INDEX_NAME`
  to the identity id. It removes the attribute when it removes the `WhoSession`. who uses the string
  constant, not Spring Session's class, so who needs no Spring Session dependency. With Spring Session
  on the classpath, `FindByIndexNameSessionRepository.findByPrincipalName(identityId)` then finds every
  session of an identity. That is the basis for "sign out everywhere", which an app builds by deleting
  those sessions. who documents it, but adds no endpoint for it in 0.12.
- **Proof.** A who-autoconfigure test runs with `spring-session-jdbc` (test scope) on PostgreSQL. It
  signs in by email link and checks two things: `findByPrincipalName(identityId)` finds the session,
  and the session's attributes are `WhoSession` and the principal index only. Passkey ceremony
  options may also be present during a ceremony.

## 2. RBAC lookups

From the template's owner bootstrap, which had to catch `RoleNotFoundException` to ask whether a
role exists:

- `Optional<Role> findRole(String name)` and `<R extends Enum<R>> Optional<Role> findRole(R role)`.
- `List<Role> listRoles()`, sorted by name.
- `List<UUID> findIdentityIdsWithRole(Role role)`, sorted by identity id.
- `createRole` on a duplicate name throws `RoleAlreadyExistsException`. It extends
  `IllegalArgumentException`, which is what it throws today, so existing `catch` blocks keep working.

## 3. Email-link issuing reports its outcome

From the template's invitations: a failed send was invisible to the owner who invited.

- `EmailLinkIssuer.issue(String address, String tokenValue)` returns `EmailLinkOutcome`, an enum
  with the values `SENT`, `UNKNOWN_ADDRESS`, `INACTIVE_IDENTITY`, `RESEND_SUPPRESSED` and
  `SEND_FAILED`. It still never throws.
- `/ott/generate` is unchanged: it answers 202 at once and ignores the outcome, so nothing reveals
  whether an address is known.
- The Javadoc states that `issue` is synchronous and uses its own transactions. A caller in a
  transaction should call it after commit (for example from `TransactionSynchronization.afterCommit`
  with `REQUIRES_NEW`, as the template does).

## 4. Test support: `who-test`

A new module, `org.jwcarman.who:who-test`, for apps' tests (test scope):

- `WhoTestSessions.signedIn(UUID identityId, UUID credentialId)` returns a `MockHttpSession` holding
  a `WhoSession` signed in now. who re-resolves it from the database on every request, as in
  production.
- `WhoMockMvcBrowser` wraps a `MockMvc`. It keeps one session and its cookies across requests, and
  it echoes the `XSRF-TOKEN` cookie into `X-XSRF-TOKEN` on unsafe requests, as an SPA does with
  `csrf.spa()`. Spring Security Test's `csrf().asHeader()` sends a masked token, which `csrf.spa()`
  rejects.
- Passkey ceremony test support (an emulated authenticator) is out of scope for 0.12.

## 5. Docs

- `docs/guides/passkeys.md`: correct which registration endpoints a chain's
  `anyRequest().authenticated()` can protect, per the template's final review.
- A "Sessions" guide covering:
  - what who stores;
  - Spring Session JDBC setup, including its tables in Liquibase;
  - "sign out everywhere" with `findByPrincipalName`;
  - timeouts and cookie flags.
- A testing guide for `who-test`.

## Out of scope

- A typed sign-in code (plan 4, a later release).
- Passkey test emulation.
- An endpoint for "sign out everywhere".
- Spring Session as a who dependency.
