# who 0.14: errors are exceptions, the application formats them

## Why

who writes its own error bodies today, in a format of its own:

| Where | Status and body today |
|---|---|
| Sign-in failure, email link (`JsonAuthenticationHandlers.failure()`) | 401 `{"error":"invalid_token"}` |
| Sign-in failure, passkey (`failure(INVALID_CREDENTIAL)`) | 401 `{"error":"invalid_credential"}` |
| Passkey registration, signed out (`PasskeyRegistrationGuardFilter`) | 401, empty body |
| Passkey registration, outside the re-sign-in window | 401 `{"error":"reauthentication_required"}` |
| Passkey registration that fails verification | 400 `{"error":"invalid_registration"}` |
| Protected request while signed out (`PasswordlessConfigurer`'s `HttpStatusEntryPoint`) | 401, empty body |
| Signed in but not permitted (`@RequiresPermission`, Spring's default handler) | 403, empty body |
| `GET /who/me` while signed out (`WhoMeController`) | 401, empty body |

An application that answers its own errors as RFC 9457 Problem Details (the noir app template is moving to that) then has two formats on the wire, and its client must understand both.

## Decision

who formats no error responses. It throws exceptions and lets the application map them, in whatever way the application already uses for its own errors.

- Errors raised inside Spring Security's filters never reach an application's `@RestControllerAdvice` on their own. who hands each one to the application's `HandlerExceptionResolver`, the same chain Spring MVC uses for controller exceptions. One `@RestControllerAdvice` therefore covers who's errors and the application's.
- When nothing in the application handles an exception, who falls back to `response.sendError(status)`. That is the servlet container's native path, so Spring Boot's own error handling answers with the application's default error body. who never writes a body itself.
- Each who exception carries its status as `@ResponseStatus`. That is metadata Spring reads natively, not a format.

who is pre-1.0 and keeps no backward compatibility: this is a breaking change in 0.14.0.

## Evidence (spike, 2026-11-10)

The spike was a throwaway Spring Boot 4.1.2 app with Spring Security, called over a real HTTP port, with an advice that marks every body it writes:

- **A filter that throws an `AuthenticationException`:** 500 with Boot's error JSON. The advice is not reached.
- **The default entry point, signed out:** 403 with Boot's error JSON. The advice is not reached.
- **A failure handler that writes its own body (who today):** that body. The advice is not reached.
- **A controller that throws `AccessDeniedException`:** reaches the advice, because the exception is raised inside MVC.
- **A failure handler, filter or entry point that hands off to `HandlerExceptionResolver`:** reaches the advice, with the original exception type (for example `BadCredentialsException`).
- **A handoff of an exception nothing maps:** `sendError` gives Boot's native error body with the fallback status.

## Design

### Exceptions

All new exceptions are in `who-spring-security`, package `org.jwcarman.who.spring.security.web`, and none carries request or credential data in its message.

| Exception | Extends | `@ResponseStatus` | Thrown when |
|---|---|---|---|
| `SignInFailedException` | `AuthenticationException` | 401 | a sign-in attempt fails (bad, expired or used token; unknown or invalid passkey; inactive identity). It wraps Spring's cause and has one fixed message, `"Sign-in failed"`, so the reason never leaks. |
| `NotSignedInException` | `AuthenticationException` | 401 | a request needs a signed-in caller and has none (the entry point, `/who/me`, passkey registration while signed out) |
| `ReauthenticationRequiredException` | `AuthenticationException` | 401 | passkey registration outside the registration window |
| `InvalidPasskeyRegistrationException` | `RuntimeException` | 400 | a passkey registration fails verification. It has no cause attached, because WebAuthn payload details must not travel. |

Access denial stays Spring Security's own `AccessDeniedException` (403): who adds no type for it.

### Handing exceptions to the application

- A small `WhoExceptionHandoff` in `who-spring-security`, built from the application's `HandlerExceptionResolver`:
  - `handOff(request, response, exception, fallbackStatus)` calls `resolver.resolveException(request, response, null, exception)`.
  - When that returns `null` (nothing handled it), or there is no resolver at all, it calls `response.sendError(status)`. The status is the exception's `@ResponseStatus`, or `fallbackStatus` when it has none.
  - It writes nothing itself.
- It finds the application's `HandlerExceptionResolver` through the context's `handlerExceptionResolver` bean (Spring MVC's composite). Without Spring MVC it uses `sendError` only.
- Its users:
  - **The sign-in failure handler.** `JsonAuthenticationHandlers.failure()` becomes a handler that wraps the cause in `SignInFailedException` and hands it off. `failure(String errorCode)` is removed, and so are the `INVALID_CREDENTIAL` and `invalid_token` codes.
  - **`PasswordlessConfigurer`.** It sets an `AuthenticationEntryPoint` that hands off `NotSignedInException`, and an `AccessDeniedHandler` that hands off the `AccessDeniedException` (fallback 403). These replace `HttpStatusEntryPoint` and Spring's default 403.
  - **`PasskeyRegistrationGuardFilter`.** It hands off `NotSignedInException`, `ReauthenticationRequiredException` and `InvalidPasskeyRegistrationException`. It loses its `JsonMapper` and its error codes.
- `WhoMeController` throws `NotSignedInException` when there is no principal, so it travels through MVC like any controller exception.
- **Success responses are unchanged.** `JsonAuthenticationHandlers.success()` still answers `{"identityId": …}`, and the email-link request still answers 202. They are not errors.

### Autoconfiguration

- `WhoAutoConfiguration` builds `WhoExceptionHandoff` with the `handlerExceptionResolver` bean when it exists.
- `JsonAuthenticationHandlers` takes the handoff instead of building error bodies. It keeps its `JsonMapper` for the success body.
- An application can replace any of these beans (`@ConditionalOnMissingBean`).

### who-example and docs

- `who-example` gets a `@RestControllerAdvice` that maps who's exceptions to Problem Details. It shows the intended use, and its tests prove the handoff reaches the advice from inside the filters.
- A new guide, `docs/guides/errors.md`, covers:
  - the exception table;
  - that errors raised in the filters reach the application's advice;
  - the `sendError` fallback;
  - a Problem Details example.
- The guides that show `{"error": …}` bodies are updated.
- The CHANGELOG `[Unreleased]` section gets a "Breaking changes" entry listing the removed bodies and codes, and what replaces them.

## Testing

- **Unit tests for `WhoExceptionHandoff`:**
  - with a resolver that handles the exception, nothing else happens;
  - with a resolver that returns `null`, `sendError` is called with the exception's `@ResponseStatus`;
  - with no `@ResponseStatus`, the fallback status is used;
  - with no resolver, `sendError` alone.
- **Each former error path:**
  - **With an application advice present:** a MockMvc test with a test `@RestControllerAdvice` that answers each who exception with a recognizable body. It proves every path reaches the advice: sign-in failure (email link and passkey), signed-out protected request, `/who/me`, missing permission, and passkey registration signed out, outside the window, and failing verification.
  - **With no advice:** the same requests answer with the right status (401, 401, 401, 403, 401, 401, 400) and no who-written body.
- **No leakage:** `SignInFailedException`'s message is fixed, and `InvalidPasskeyRegistrationException` has no cause.
- `who-example`'s tests cover its Problem Details advice end to end.

## Out of scope

- Any Problem Details code in who itself. The application owns its format.
- The noir app template's global advice, Bean Validation mapping and client parser. That is a separate plan in `noir-app-template`, which will map who's exceptions.
